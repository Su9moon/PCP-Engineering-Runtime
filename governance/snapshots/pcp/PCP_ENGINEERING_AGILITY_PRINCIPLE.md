# PCP Core｜工程敏捷与禁止人为设障原则

- **状态**：用户直接明确要求，自 2026-10-18 起作为 PCP 跨项目工程执行原则。
- **适用**：PCP Core、EO、ES、HB、Codex Bridge，以及采纳 PCP 工程执行方式的业务/实例仓库。
- **性质**：工程执行原则，**不是新 Gate、新审批环节、新服务或新治理系统**。不重写历史 FIXED Baseline，不自动改变业务事实或运行权限。

## 核心要求（用户原意）

> 不再自行增加固定分支、固定文件数量、额外版本身份或人为审批关卡来限制正常开发和升级。以后绝对不可以再发生这种情况。

这一要求优先约束 AI/Agent **自行设计**的开发流程与实施选项：**除非用户明确要求，或有可证明且不可规避的技术/安全/数据保护约束，AI 不得增设与目标无关的限制，也不得沿用已失效的旧阶段限制妨碍当前已批准的目标。**

## 必须执行

1. **目标优先**：从用户现行目标及真实运行事实出发；不要让早期 MVP 的临时规则反过来定义当前完整版本。
2. **不自行设障**：不得把固定 Git 分支名称、特定文件数量/白名单子集、旧版代码布局、额外版本身份、额外审批关卡、无必要的 Gate/锁/流程/状态当成日常开发或升级的硬性前提。
3. **复用与最小变更**：优先复用现有实例、已有发行/源码/账号/工作区和成熟工具；不得以“升级”为由默认新增一套实例、目录树、调度器或通用管理层。
4. **识别历史约束**：历史 Baseline、旧阶段 workorder、代码中的硬编码可能只属于历史实现。发现它与用户新目标冲突时，先准确定位，再修正/替换不合理旧约束，不要求新目标迁就旧假设。
5. **不扩大授权**：业务数据、生产停启、凭据、破坏性 Git 操作、真实项目写入等既有实质安全边界继续有效；不得借“减少关卡”擅自修改生产或超出当前授权。
6. **必须提出限制时**：只有技术上确有必要（例如数据完整性、认证、进程身份、安全隔离），才说明具体失败事实、目标风险和最小可行保护；不能把助手偏好、预防性想象、重复验收或流程便利包装成强制限制。
7. **简单可用优先**：能够通过已有机制完成的任务直接做；必要检查仅检查会改变结果的事实。可选优化后置，避免多层方案、重复问询与流程膨胀。

## 执行解释

- 用户已授权范围内的正常开发与升级：**不得人为要求第二次重复批准**。
- 超出当前授权范围的生产发布、危险操作或破坏性修改：仍需按真实权限与风险确认，不能暗中越权。
- 先判断“这条限制是谁要求的、为了解决什么**当前仍存在**的具体风险”。若缺少现行用户要求或有效技术依据，**不引入；已存在且造成阻塞则纠正或废弃**。
- 通过 GitHub Issue / PR / commit 保留已有工程事实与可追溯证据即可；**不要为贯彻本原则再创造新的审批 Gate、报告仪表盘或运行服务**。

## 实际教训｜Codex Bridge Dev→Green（2026-10-18）

- E0a 遗留的固定分支 `rm0/dev-lane-work` 与正在推进的 Git 分支不一致，导致运维检查无意义地失败。
- E0a Release 仅接受指定路径内的少量源码文件，而完整 Blue RC2/HF1 发行含 147 个文件；旧子集规则不应限制将现有 Dev 升级为完整 Green。
- 用户要的是**复用当前 Dev 原地升级为第二套独立完整 RC2/HF1**，不是创建第三套实例，更不是先重建额外治理框架。
- 事件与整改详情见 `Su9moon/codex-bridge` Issue #85；本文件保留可跨项目复用的原则，不复制项目内部运行手册。
